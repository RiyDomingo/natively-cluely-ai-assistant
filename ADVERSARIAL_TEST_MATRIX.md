# Natively v2.8.8 Proposed Adversarial Test Matrix

## Status

This matrix records the initial local campaign, the F-001 remediation regressions, and the remaining proposed tests. H-001 and the read-only part of H-002 were reproduced and then locally remediated on 2026-10-01; other rows remain pending. H-001 now passes against a fresh macOS arm64 electron-builder directory package (not just a fixture). Windows CI has been added but not run; signed release-artifact regressions remain required. **Pending** is not a security finding. “Static evidence” records only why a test is prioritized. Final results use one of the five required classifications only after reproducible evidence exists:

1. Control works as intended.
2. Control partially works.
3. Control can be bypassed.
4. Apparent bypass without meaningful impact.
5. Cannot safely complete from the available environment.

Severity is a provisional impact estimate assuming the hypothesis is confirmed. It must be revised for prerequisites and demonstrated impact after testing.

## Safety and evidence rules

- Run only against a disposable local user-data directory and local build that we control.
- Use synthetic documents, credentials, OAuth bundles, licence responses, and model/provider stubs. Do not call real OAuth, licence, telemetry, AI-provider, update, or other third-party endpoints.
- Bind network fixtures to loopback. LAN cases should use an isolated local interface or mocked socket metadata, not other devices.
- Never collect real credentials, persist outside the disposable profile, modify the installed production application, or initialize missing private submodules.
- Capture command, build mode, environment, fixture hash, expected result, actual result, and relevant redacted log excerpt for every run.
- A suspected failure must reproduce twice, then be reduced to the smallest regression test before it is classified as a bypass.

## Proposed execution order

1. **Release-boundary tests:** H-001, H-002, H-003, H-006, H-010, H-030, H-031, H-034, H-035. These have the largest plausible authorization, privacy, or code-execution impact.
2. **State and credential tests:** H-004, H-005, H-008, H-012 through H-016, H-032, H-033.
3. **Local service and input tests:** H-017 through H-027.
4. **Prompt and path-consistency tests:** H-028 and H-029, beginning with deterministic structural assertions before model-behaviour evaluation.
5. **Lower-impact resilience/policy tests:** H-007, H-011, H-013, H-020, H-021, H-036.

## Proposed test artifacts after approval

- A centralized channel/entitlement policy manifest used only by tests at first.
- Focused Node/Electron tests under the repository's existing `electron/**/__tests__/*.test.mjs` convention.
- Pure unit/property tests for date parsing, credential state transitions, URL policy, path identity, redaction, and prompt serialization.
- Loopback-only integration fixtures for OAuth callback, Phone Mirror, URL fetch/redirect, provider transports, and updater feeds.
- Packaged-artifact smoke tests for E2E surface absence, navigation policy, CSP/rendering, source-map contents, and signed-update eligibility.

Production remediations should not be implemented until a hypothesis is reproduced, impact is established, and the smallest regression test is in place.
